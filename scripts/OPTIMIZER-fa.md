# بهینه‌ساز سرور پاسارگارد

`scripts/optimizer.sh` یک سرور اوبونتو ۲۲.۰۴ را که پنل پاسارگارد روی آن اجرا
می‌شود، برای دیپلوی‌های بزرگ تیون می‌کند. مقادیر پیش‌فرض برای سروری در حدود
۸ هسته و ۳۲ گیگابایت رم با چند صد هزار کاربر تنظیم شده‌اند.

اسکریپت idempotent است (اجرای چندباره مشکلی ایجاد نمی‌کند)، از هر فایلی که
تغییر می‌دهد بکاپ می‌گیرد، و می‌تواند تغییراتش را برگرداند.

</div>

```bash
sudo ./scripts/optimizer.sh --check      # فقط گزارش، هیچ تغییری نمی‌دهد
sudo ./scripts/optimizer.sh --dry-run    # نمایش تمام تغییرات همراه با diff
sudo ./scripts/optimizer.sh              # اعمال
sudo ./scripts/optimizer.sh --rollback latest
```

## پروفایل‌ها

| پروفایل | برای چه سروری | تفاوت |
| --- | --- | --- |
| `panel` (پیش‌فرض) | سرور پنل و دیتابیس | conntrack متناسب با ترافیک API |
| `node` | سرور نود Xray | conntrack دو برابر، فعال‌سازی IP forwarding |
| `all-in-one` | پنل و Xray روی یک سرور | هر دو مورد بالا |

## ماژول‌ها

با `--only sysctl,limits` فقط بخشی را اجرا کنید یا با `--skip swap` یکی را
کنار بگذارید.

| ماژول | چه چیزی را تغییر می‌دهد |
| --- | --- |
| `sysctl` | فایل `99-pasarguard-optimizer.conf` — شبکه، conntrack، حافظه، محدودیت فایل |
| `limits` | `limits.d` و `DefaultLimitNOFILE` سیستم‌دی و drop-in هر سرویس |
| `thp` | غیرفعال‌کردن transparent huge pages (ماندگار بعد از ریبوت) |
| `swap` | ساخت فایل swap اگر سرور swap نداشته باشد |
| `io` | قوانین udev برای زمان‌بند دیسک، عمق صف و read-ahead |
| `cpu` | تنظیم گاورنر CPU روی `performance` در صورت وجود cpufreq |
| `nic` | بافر رینگ، offload، RPS/XPS و txqueuelen — بعد از ریبوت دوباره اعمال می‌شود |
| `docker` | `daemon.json`: چرخش لاگ، ulimit و `live-restore` |
| `journald` | محدودکردن حجم ژورنال و اضافه‌کردن rate limit |
| `database` | تیون PostgreSQL یا MySQL بر اساس رم و تعداد هسته سرور |
| `nginx` | `worker_rlimit_nofile`، `worker_connections` و تنظیمات سطح http |
| `services` | irqbalance، همگام‌سازی ساعت، غیرفعال‌کردن apport/whoopsie |
| `env` | تولید (و در صورت درخواست، اعمال) تنظیمات `.env` پنل |

## دقیقاً چه چیزی تیون می‌شود و چرا

### سوکت‌ها و file descriptorها

با این تعداد کاربر، پنل عملاً یک ماشین تولید سوکت است: هر دریافت ساب‌اسکریپشن
یک کانکشن کوتاه‌عمر است و هر اتصال نود یک استریم gRPC طولانی‌مدت. مقادیر
پیش‌فرض اوبونتو برای یک دسکتاپ تنظیم شده‌اند، نه چنین باری.

- `nofile` برای نشست‌های لاگین، سرویس‌های systemd و مشخصاً یونیت‌های
  `docker`، `pasarguard`، `postgresql` و `nginx` به ۱٬۰۴۸٬۵۷۶ می‌رسد.
- `net.core.somaxconn` و `tcp_max_syn_backlog` به ۶۵۵۳۵ می‌رسند تا بار ناگهانی
  در صف بماند و در accept queue دور ریخته نشود.
- بازه `ip_local_port_range` بازتر می‌شود و `tcp_fin_timeout` و `tcp_tw_reuse`
  سخت‌گیرانه‌تر می‌شوند تا پورت‌های خروجی به‌موقع آزاد شوند.
- `tcp_keepalive_time` به ۵ دقیقه کاهش می‌یابد تا سوکت‌های مرده کلاینت‌ها
  به‌جای دو ساعت، سریع پاک شوند.

### کنترل ازدحام

BBR به‌همراه qdisc با نام `fq`، در صورتی که کرنل `tcp_bbr` داشته باشد
(اوبونتو ۲۲.۰۴ دارد). مقدار `tcp_slow_start_after_idle=0` جلوی این را می‌گیرد
که یک کانکشن keepalive دوباره از slow start شروع کند — این برای استریم‌های
node-bridge اهمیت دارد.

### ردیابی کانکشن (conntrack)

مقدار `nf_conntrack_max` از روی رم محاسبه می‌شود (`RAM_bytes / 16384 / 2`،
همان قاعده خود کرنل)، به مضربی از ۶۴K گرد می‌شود و در پروفایل `node` دو برابر
می‌شود. روی ۳۲ گیگابایت چیزی حدود یک میلیون رکورد می‌شود — تقریباً ۳۲۰
مگابایت حافظه کرنل.

تایم‌اوت `established` از **۵ روز** پیش‌فرض به ۱ ساعت کاهش می‌یابد؛ این
مهم‌ترین دلیل پرشدن جدول conntrack روی سرورهای پروکسی است.

با `--conntrack-max N` می‌توانید مقدار دلخواه بدهید. حالت `--check` میزان
مصرف واقعی جدول را گزارش می‌دهد؛ بالای حدود ۷۰٪ یعنی وقت افزایش آن است.

### دیتابیس

مقادیر از روی رم و تعداد هسته‌های شناسایی‌شده محاسبه می‌شوند، نه hardcode.
روی سرور ۳۲ گیگ / ۸ هسته تقریباً به این مقادیر می‌رسد:

| تنظیم | مقدار | دلیل |
| --- | --- | --- |
| `shared_buffers` | ۸ گیگابایت | ۲۵٪ رم، حداکثر ۱۲ گیگابایت |
| `effective_cache_size` | ~۱۷ گیگابایت | ۵۵٪ رم |
| `max_connections` | ~۲۰۰ | `workers × (pool + overflow)` به‌علاوه فضای اضافه |
| `work_mem` | ~۲۴ مگابایت | ۱۵٪ رم تقسیم بر تعداد کانکشن |
| `autovacuum_vacuum_scale_factor` | ۰.۰۲ | مقدار پیش‌فرض ۰.۲ باعث انباشت dead tupleها روی جدول‌های مصرف می‌شود |
| `jit` | خاموش | برای کوئری‌های کوتاه OLTP بیشتر هزینه دارد تا فایده |
| `synchronous_commit` | خاموش | بخش «ماندگاری داده» را ببینید |

بعد از نوشتن فایل، اسکریپت آن را دقیقاً همان‌طور که خود سرور پارس می‌کند
بررسی می‌کند (`postgres -C shared_buffers`) و اگر PostgreSQL آن را نپذیرد،
فایل را برمی‌گرداند.

**ماندگاری داده.** حالت پیش‌فرض `--db-durability balanced` مقدار
`synchronous_commit = off` (در PostgreSQL) و `innodb_flush_log_at_trx_commit = 2`
(در MySQL) را تنظیم می‌کند. در این حالت، کرش سخت یا قطع برق می‌تواند حدود
یک ثانیه از تراکنش‌های کامیت‌شده را از بین ببرد — برای این بار کاری یعنی
یک ثانیه از شمارنده‌های مصرف. دیتابیس **هرگز** خراب نمی‌شود؛ فقط جدیدترین
کامیت‌ها از دست می‌روند. اگر fsync کامل می‌خواهید، از
`--db-durability strict` استفاده کنید.

تغییر `max_connections` و `shared_buffers` نیاز به **ری‌استارت کامل** دارد،
نه reload.

### تنظیمات پنل

با `--apply-env` فایل `.env` پنل مستقیماً تغییر می‌کند (بعد از بکاپ‌گرفتن).
بدون این سوییچ، پیشنهادها فقط در این مسیر نوشته می‌شوند تا بررسی کنید:
`/var/lib/pasarguard-optimizer/reports/env-recommendations.env`

دو تغییری که در مقیاس بالا بیشترین اثر را دارند:

**تعداد ورکرها.** یک ورکر uvicorn نمی‌تواند از ۸ هسته استفاده کند. اسکریپت
`UVICORN_WORKERS = cores × 3/4` را پیشنهاد می‌دهد تا برای PostgreSQL و
node-bridge هم جا بماند. اما `main.py` تابع `require_nats_if_multiworker()`
را صدا می‌زند: **بیش از یک ورکر بدون NATS اصلاً بالا نمی‌آید.** برای همین
اسکریپت اول `NATS_URL` را تست می‌کند و اگر NATS در دسترس نباشد،
`UVICORN_WORKERS = 1` را نگه می‌دارد تا کانفیگی به شما ندهد که پنل را از کار
بیندازد. بعد از راه‌اندازی NATS، دوباره اجرا کنید:

</div>

```bash
sudo ./scripts/optimizer.sh --only env --apply-env
```

<div dir="rtl">

**فاصله اجرای جاب‌ها.** هر جاب پس‌زمینه در `app/jobs/` کل جدول کاربران را
پیمایش می‌کند. با ۳۰۰ هزار کاربر، مقادیر پیش‌فرض
(`JOB_REVIEW_USERS_INTERVAL = 30` و `JOB_RECORD_USER_USAGES_INTERVAL = 10`)
یعنی یک پیمایش جدید قبل از تمام‌شدن قبلی شروع می‌شود، اجراها روی هم انباشته
می‌شوند و دیتابیس هیچ‌وقت بی‌کار نمی‌ماند. مقادیر پیشنهادی تقریباً دو برابر
می‌شوند.

یادتان باشد سقف کانکشن برای هر پروسه جداست:
`(SQLALCHEMY_POOL_SIZE + SQLALCHEMY_MAX_OVERFLOW) × UVICORN_WORKERS`.
اگر تعداد ورکر را بالا بردید، باید `max_connections` دیتابیس را هم بالا ببرید.

## برگرداندن تغییرات (Rollback)

هر اجرا یک مجموعه بکاپ در `/var/lib/pasarguard-optimizer/backups/` می‌سازد.

</div>

```bash
sudo ./scripts/optimizer.sh --list-backups
sudo ./scripts/optimizer.sh --rollback 20260115-104233
sudo ./scripts/optimizer.sh --rollback latest
```

<div dir="rtl">

فایل‌هایی که قبل از اجرا وجود داشتند بازگردانده می‌شوند و فایل‌هایی که
اسکریپت ساخته حذف می‌شوند. بعدش سرویس‌های مربوطه را ری‌استارت کنید.

## بررسی بعد از اجرا

</div>

```bash
sudo ./scripts/optimizer.sh --check
```

<div dir="rtl">

مواردی که ارزش دارد چند روز اول زیر نظر بگیرید:

- **مصرف conntrack** — بالای ۷۰٪ یعنی `--conntrack-max` را بالا ببرید.
- **تعداد TIME-WAIT در `ss -s`** — باید خیلی کمتر از بازه پورت محلی بماند.
- **تعداد رکوردهای `pg_stat_activity` نسبت به `max_connections`** — اگر پر شد،
  یا اندازه pool را کم کنید یا `max_connections` را زیاد کنید.
- **حافظه** — مجموع `shared_buffers` و `work_mem × connections` و ورکرهای پنل
  باید در رم جا شود و برای page cache هم فضا بماند.

## نکات مهم

- کانتینرهای **LXC / OpenVZ** مالک بیشتر تنظیمات کرنل نیستند. اسکریپت این را
  تشخیص می‌دهد، هر چه می‌تواند اعمال می‌کند و نام تمام کلیدهایی که کرنل رد
  کرده را گزارش می‌دهد.
- **محدودیت لاگ داکر** فقط برای کانتینرهای جدید اعمال می‌شود. کانتینرهای
  موجود تا زمانی که دوباره ساخته نشوند تنظیمات لاگ فعلی‌شان را نگه می‌دارند
  (`docker compose up -d --force-recreate`).
- **`nofile` در شل‌های باز** تغییر نمی‌کند؛ باید دوباره لاگین کنید یا ریبوت.
- **PgBouncer** بالای حدود ۸ ورکر ارزش بررسی دارد، اما درایور asyncpg در
  SQLAlchemy از prepared statement استفاده می‌کند، پس حالت transaction pooling
  نیاز به `statement_cache_size=0` روی کانکشن دارد. اسکریپت این را راه‌اندازی
  نمی‌کند.
- اسکریپت هیچ‌وقت به قوانین فایروال، گواهی‌های TLS یا دیتای پنل دست نمی‌زند.
